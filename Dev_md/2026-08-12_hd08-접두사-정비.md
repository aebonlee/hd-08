# 2026-08-12 — hd-08 접두사 정비와 배포 경로 복구

강의 중 실습으로 만든 회원가입 페이지를 정식 규칙에 맞게 고쳤다.
로컬 클론(`dreamit-web/hd-08`)을 뜨고 그 위에서 작업했다.

## 왜 손댔나

Supabase는 전 사이트가 **한 프로젝트를 공유**한다(§3.1). 그런데 이 리포의 스키마는
`site_member_profiles`처럼 접두사 없는 이름을 쓰고 있었다. 이대로 두면
다음 실습 사이트가 같은 이름을 만들 때 부딪히고, 누가 어느 사이트 것인지도 구분이 안 된다.

배포 쪽에도 구멍이 있었다. `deploy-pages.yml`이 **리포 루트**에 있었다.
Actions는 `.github/workflows/` 아래만 읽으므로 이 워크플로는 한 번도 돈 적이 없다.
Pages는 `build_type: legacy`, `source: main /` 상태로 소스의 `index.html`을 그대로 서빙 중이었고,
`__SUPABASE_URL__` 자리표시자가 치환되지 않은 채 나가고 있었다.
**fallback 상수 덕분에 우연히 동작하고 있었을 뿐**이다.

## 한 일

### 1. `hd08_` 접두사 스키마 — `supabase/2026-08-12_hd08_membership.sql`

| 옛 이름 | 새 이름 |
|---|---|
| `site_member_profiles` | `hd08_profiles` |
| `handle_site_member_signup()` | `hd08_handle_signup()` |
| `set_site_member_updated_at()` | `hd08_set_updated_at()` |
| `on_auth_user_created_site_member_profiles` | `hd08_on_auth_user_created` |
| `site_member_select_own` / `_update_own` | `hd08_profiles_select_own` / `_update_own` |

**이미 만들어 둔 것이 있으면 DROP하지 않고 RENAME한다.** 강의 중 수강생이 가입했을 수 있어서다.
단 `ALTER TABLE ... RENAME`은 제약조건 이름을 바꾸지 않으므로, `pg_constraint`를 훑어
`RENAME CONSTRAINT`를 따로 돌린다. 이걸 빼면 `site_member_profiles_pkey` 같은 이름이 그대로 남는다.

함께 고친 것:

- **`site_code` 빈 문자열이면 가입이 통째로 실패하던 버그.**
  원본은 `nullif(v_site_code, '')`를 `not null` 컬럼에 넣었다.
  메타데이터로 `site_code: ""`가 오면 NULL이 되어 NOT NULL 위반으로 죽는다.
  `coalesce(nullif(...), 'hd-08')`으로 바꿨다.
- **함수 권한.** 원본은 `revoke ... from public`만 했다. 권한은 두 겹으로 붙는다 —
  PostgreSQL이 PUBLIC에 주는 기본값과, **Supabase가 `ALTER DEFAULT PRIVILEGES`로
  신규 함수마다 anon에 자동 부여하는 것**. PUBLIC만 지우면 `anon=X`가 남는다.
  `from anon`을 따로 REVOKE했다. 트리거 전용 함수라 `authenticated`는 남겨 뒀다(§3.7).
- 이메일이 비면 가입을 막는 검사 추가(`email`이 `not null unique`인데 `''`가 들어가면
  두 번째 사용자에서 유니크 충돌이 난다).

트리거는 `signup_source = 'hd08-membership-v1'`일 때만 발화한다. 이 프로젝트에는
사이트 수십 곳의 가입이 함께 들어오므로, 조건 없이 걸면 여기서 raise한 예외가
**전 사이트 가입을 마비**시킨다(2026-06-19에 실제로 겪은 사고다).
이 문자열은 `index.html`의 `SIGNUP_SOURCE`와 한 글자도 달라선 안 된다.

### 2. 로컬 PostgreSQL 검증 — `scripts/sqltest/`

`tsc`도 `vite build`도 SQL을 잡아 주지 않는다. 운영에서 처음 돌리지 않으려고 하네스를 만들었다.

```
scripts/sqltest/run.sh          # 두 시나리오 검증
scripts/sqltest/run.sh --break  # 하네스가 실패를 실제로 잡는지 확인
```

임시 PG17 클러스터를 띄우고 Supabase 환경(anon/authenticated/service_role 역할,
`auth.users`, `auth.uid()`, 그리고 **함수 EXECUTE 자동 부여까지**) 스텁을 세운 뒤 실제로 적용한다.

- 시나리오 A(fresh): 빈 DB → 적용 → **한 번 더 적용**(재실행 안전성) → ASSERT 17건 + updated_at 1건
- 시나리오 B(legacy): 옛 무접두사 스키마 + 가입 1건 → 적용 → 위 전부 + 이관 ASSERT 2건

**일부러 깨뜨려 하네스를 검증했다.** `--break`는 `anon` REVOKE 한 줄을 뺀 사본으로 돌리는데,
`[10] hd08_ 함수 1건에 anon EXECUTE가 남아 있다`로 정확히 잡고 멈춘다.
통과만 본 테스트는 의미가 없다.

검증용 SQL은 `supabase/`에 두지 않았다. 그 폴더의 다른 파일은 전부 "SQL Editor에서 실행하라"는
안내라서 **폴더가 주는 신호가 주석보다 세다.** 대신 `.local.sql`에 가드를 넣어
`supabase_admin`·`authenticator` 역할이나 `graphql` 스키마가 보이면 스스로 중단하게 했다.
적어 두는 대신 실행할 수 없게 만든 것이다.

### 4. 배포 경로

`deploy-pages.yml`을 `.github/workflows/`로 옮기고, 루트의 죽은 사본과
옛 `supabase_membership.sql`을 지웠다. 워크플로도 두 군데 고쳤다.

- **변수가 없어도 배포를 막지 않는다.** 원본은 `SUPABASE_URL`이 비면 `exit 1`이었다.
  index.html에 fallback이 있어 치환 없이도 페이지는 동작하는데,
  변수 미등록 하나로 배포 전체를 죽이면 사이트가 옛 내용에 묶인다. 경고만 남기고 진행한다.
- **비밀 키 유출 가드.** 산출물에 `sb_secret_`·`service_role`이 보이면 배포를 중단한다.

세 경로(변수 없음 / 변수 있음 / 비밀 키 섞임)를 로컬에서 실제로 돌려 확인했다.

## 남은 것

- **리포가 public이다.** §3.8 1층은 자체 제작 리포를 전부 private으로 둔다.
  강의 실습물이라 의도적으로 열어 둔 것인지 확인이 필요하다.
- 이 사이트는 `www_profiles` 통합 회원 체계(§3.3)와 **별개 테이블**을 쓴다.
  실습이라 그대로 두었지만, 실제 운영으로 올리려면 www 총괄에서 안 보인다.
- 사이트 카탈로그·www 레지스트리(§3.11)에는 등록하지 않았다. 실습물이라 판단했다.
